# 공식 혜택 데이터 운영

## 설계와 출처

React/Vite, localStorage, 하단 탭, 기존 카드 4장·자동결제·백업 구조를 유지한다. 별도 DB나 런타임 카드사 scraping은 없다. `reviewed.mjs`의 검토 사실 → 검증 → `official-benefits.json` → Vite 번들 순서다.

현대의 현재 상품 페이지는 다른 Edition과 혼동할 수 있어 Edition1이 명시된 공식 PDF를 사용한다. 다른 Edition을 이름으로 추정하거나 최신 상품으로 치환하지 않는다. KB는 문구만으로 식별할 수 없으므로 연결 전 수치를 표시하지 않는다. NH도 PACK을 선택하기 전 금액 비교를 보류한다. 삼성은 기존 `edition: taptap O`와 카드 ID가 일치할 때만 기존 상품을 연결하며 패키지 미확인은 조건부 상한으로 안내한다. 다른 삼성 상품은 연결을 해제한다.

블로그·커뮤니티·비교 사이트 수치는 사용하지 않는다. 공통 제외사항은 읽기 쉬운 요약이며 전체 약관은 각 공식 링크에서 확인한다. 스마트 적립처럼 월 전체 이용 내역이 필요한 항목은 설명만 표시하고 임의 계산하지 않는다.

## 정규화 필드

- 상품: `id`, `cardId`, `name`, `sourceId`, `benefits`
- 혜택: `merchant`, `keywords`(정규화 후 정확히 일치), `category`, `scope`(특정 가맹점/국내 일반/국내외/해외)
- 수치: `type`(discount/points/cashback/service), `rate`(% 단위), `flatAmount`, `unit`(원/P)
- 한도: `monthlyCap`, `dailyCap`, `perTransactionCap`, `frequency`(일/월/연), `monthlySpendCap`(월 적립 대상 결제액), `capGroup`(공유 영역)
- 조건: `previousSpend`, `tiers`, `minPayment`, `mode`, `packages`, `conditions`, `exclusions`, `spendExclusions`
- 증거: `sourceUrl`, `sourceId`, `checkedAt`, `status`(verified/display-only/needs-review)
- 중복: `additionalTo`는 공식 확인된 KB 기본 할인 + 자동납부 추가 할인에만 지정

`rate`와 `flatAmount` 중 하나만 계산에 사용한다. `monthlyCap: null`은 해당 데이터에서 월 금액 한도가 없음을 뜻하며 횟수 제한은 별도다. `perTransactionCap`, `dailyCap`, `frequency`의 null은 별도 제한이 기재되지 않았음을 뜻한다. 미확인 수치를 0이나 무제한으로 추정해 계산 가능한 데이터로 만들지 않는다. 수치가 불명확한 항목은 `needs-review`/`display-only`로 제외한다. 적립형의 스마트 추가 적립과 이용권은 현금 혜택으로 계산하지 않는다.

## 원문 수집 및 갱신

`adapters.mjs`는 상품별 읽기 전용 어댑터다.

- 삼성: 서버 렌더링 HTML의 Nuxt 문자열에서 혜택 블록을 읽는다. 원격 JavaScript를 실행하지 않는다.
- NH/KB: 상품의 혜택·이용조건 구간을 추출하고 필수 문구를 검증한다. 경계가 달라지면 실패한다.
- 현대: 공식 PDF를 내려받아 서명·최소 크기·전체 SHA-256으로 비교한다. 해당 서버의 TLS 호환 옵션만 허용하고 인증서 검증을 끄지 않는다.

HTML 텍스트의 공백/태그를 정리한 해시, PDF 전체 해시를 `baseline.json`에 보관한다. 동일 원문이면 검토한 구조화 값은 유지하고 최종 확인일만 갱신한다. **새 할인율을 스크립트가 추정하는 자동 파서는 아니다.** 원문이 달라졌을 때 사람의 재검토가 필요하다는 의도적인 정확성 우선 선택이다. 공지·새 PDF URL을 별도로 탐색하지 않으므로 정기적으로 상품 설명서 링크 및 공식 공지도 검토해야 한다.

각 출처는 독립적으로 갱신한다. 실패한 출처의 혜택/확인일은 바꾸지 않고 상태만 failed 또는 review로 기록한다. 파일은 임시 파일에 쓴 뒤 rename한다. 빈 목록·범위 밖 비율·잘못된 공식 URL 등은 저장 전에 검증한다. 빌드도 JSON 검증을 통과해야 한다. UI는 실패/변경/30일 경과를 구분하고 이 경우 해당 카드를 추천에서 제외한다. 새 배포를 받지 못한 기기는 확인일 경과 상태를 표시할 수 있지만 원격 실패 사실까지 실시간 알 수는 없다.

GitHub Actions는 주 1회 확인 → 테스트 → 빌드 → JSON/상태 커밋 → 정적 아티팩트 생성 순서다. 일부 출처 실패 시에도 기존 정상 혜택을 포함한 결과를 먼저 저장하고 마지막 단계에서 실행 실패를 표시한다. 브랜치 보호로 push가 막히면 기존 저장소/배포는 그대로이며 Actions 로그와 아티팩트로 확인한다. 현재 작업에서는 워크플로 파일만 준비했으며 원격 배포·스케줄 활성화는 하지 않았다.

### 내용 변경 검토 절차

1. 해당 공식 페이지와 연결된 상품설명서·공지에서 정확한 상품 코드, 수치, 조건, 제외사항을 읽는다.
2. `scripts/benefits/reviewed.mjs`를 수정한다. 카드가 달라졌다면 새 상품 ID로 추가하고 기존 상품 ID를 재사용하지 않는다. 검토일도 바꾼다.
3. `node scripts/benefits/update.mjs accept --reviewed`로 검토 기준과 JSON을 생성한다. 내려받은 자료는 git 제외 디렉터리 `.tmp/benefit-sources`에 생긴다. 이 명령은 내용을 검토했다는 유지보수자의 명시적 선언이며 주기 작업에는 넣지 않는다.
4. `npm test`, `npm run build`, 필요 시 모바일 회귀 검사를 실행한다. `benefits:build`는 검토 기준 해시와 일치하는 검토 파일만 JSON으로 변환한다.
5. JSON·기준 해시·코드를 함께 커밋하고 기존 호스팅으로 `dist`를 배포한다.

일반 갱신 명령은 기준 해시를 자동 승인하지 않는다. 기준이 없거나 달라지면 그대로 review 상태를 유지한다.

## 사용자 데이터 보호

공식 JSON은 번들에만 존재한다. 자동 갱신 스크립트는 localStorage에 접근하지 않는다. 기존 `my-cards-v1`, 버전 1 백업은 그대로 유효하며 이름·Edition 텍스트·목표·현재 실적·이력·고정비·메모·즐겨찾기·추천 규칙을 덮어쓰지 않는다. 사용자 선택값 `officialProductId`, `samsungPackage`만 선택 필드로 추가했다. 예전 백업은 두 필드 없이 복원 가능하다. 공식 선택 후에도 자유 입력 Edition 문구 자체는 보존한다.

기존 수동 요약과 초기 안내를 공식 검증 정보로 오인하지 않도록 ‘나의 혜택 메모 (미검증)’로 표시한다. 사용자 추천 규칙은 검색 결과의 참고 문구로 유지하며 금액 순위를 조작하지 않는다.

## 예상 금액 계산과 제한

전월은 현재 날짜에서 달력상 한 달 전이다. 현재월 `currentSpentKRW`, 개인 목표, 예정 자동결제를 대신 사용하지 않는다. `history[전월]`이 없으면 조건부 금액과 기록 없음 안내, 0원/기준 미달이면 0원과 미달 안내다. 신규 유예는 발급일 자료가 없으므로 자동 가정하지 않는다. 기존 이월 이력은 개인 입력 기록 기준이며 카드사 인정 실적과 다를 수 있어 직접 수정할 수 있다.

비율 또는 정액 적용 → 최소 결제액 → 건당/일/월/대상 이용금액 한도를 반영한다. NH는 전월 40만~80만원 미만이면 영역별 8천원, 80만원 이상이면 1만5천원이다. 전월 미확인은 최소 구간을 사용한다. 실제 월 소진액/일·연 횟수는 추적하지 않으므로 언제나 ‘최대 약’으로 표시한다. 공유 한도를 각각 합산하지 않으며 한 번의 가상 결제 상한을 비교한다. 여러 번 계산해도 실적/잔여한도는 차감되지 않는다.

네이버플러스 멤버십 자체 적립은 카드 적립에 더하지 않는다. 회원·적립 대상 주문/비회원은 결제 방식에서 선택한다. 공식 정기결제와 일반 결제를 구분한다. 가맹점 매칭은 잘못된 부분문자열 추천을 피하려고 정확한 별칭만 사용한다. 지점명이 붙은 임의 검색어는 인식하지 않을 수 있다. 일부 페이·PG·임대매장, 특수 결제 및 카드사 반올림 규칙은 완전하게 판정할 수 없으므로 조건을 함께 확인해야 한다. 순위는 비교 편의를 위해 1P=1원을 가정하며 보장된 현금 환산액이 아니다.

검증 예: 삼성 패키지1·전월 30만원 이상·스타벅스 1만원 → 최대 5천원. 네이버 Edition1·전월 30만원 이상·일반 1만원 → 최대 100P. 삼성 영화 9,999원 → 0원, 1만원 → 최대 5천원. KB OTT 정기결제 1만원·전월40만원 → 기본100원+추가1천원. NH 병원20만원 → 전월40만원일 때 최대8천원, 전월80만원일 때 최대1만5천원.

## 결제 추천 V2

`src/data/merchants.js`는 공식 카드 혜택과 분리된 매장 해석 사전이다. 각 항목의 `aliases`는 입력 보정, `terms`는 공식 혜택의 가맹점·업종과 비교할 키워드다. 따라서 별칭이나 지점명이 추가되어도 공식 할인율 JSON을 바꾸지 않는다. 잘못된 부분일치가 특히 위험한 동물병원은 별도 업종으로 등록해 사람 병원 혜택에서 제외한다.

추천 시 상품 확인 → 가맹점/업종 매칭 → 결제방식 조건 → 전월 인정 실적 → 한도 순서로 판단한다. 금액이 없으면 적용 가능한 가장 높은 비율을 보여 주되 원화로 환산하지 않는다. 금액이 있으면 비율 또는 정액 할인에 일·건·월 한도를 적용한다. 결제방식이 조건인 공식 혜택이 검색 결과에 있을 때만 선택지를 보여 준다.

카드 간 예상 혜택 차이가 `min(실제 차이)` 기준으로 300원 이하 또는 결제금액의 1% 이하이고, 차순위 카드의 현재월 목표가 미달이면 실적 보조 의견을 표시한다. 이 의견은 월 목표 관리용이며 전월실적 조건 판정에는 절대 사용하지 않는다. 최대 혜택 카드가 계속 첫 추천이다.

최근 검색과 사용자 매장은 localStorage의 `recentSearches`, `customMerchants`에 따로 저장한다. 이전 백업에 두 필드가 없으면 빈 배열로 보정해 복원한다. 사용자 매장 이름·업종은 공식 데이터 갱신으로 변경되지 않는다.

브라우저 검사는 기존 실적·고정비·즐겨찾기·백업/복원뿐 아니라 수치 입력·미확인 Edition·전월 0원·상품 연결·메모 보존·320/390/430px·오프라인을 확인한다. 캐시 사전 저장과 실제 모듈 요청의 `Vary: Origin` 차이로 오프라인 자산을 못 읽던 문제도 정적 자산 캐시 조회에서 보완했다.
